# M5: holdings monitor and alerts

**Done when** (PLAN.md): alerts arrive on both channels, quiet hours respected.

**Changed by you (2026-10-28): alerts go to the app only for now.** That means the site's Today screen; there's no email setup. So the finish line becomes: alerts are recorded for the app, and quiet hours are respected. You'll see them once the site is live in M6.
- **What this gives up:** push. An urgent alert, like a red-flag 8-K, is seen only when you open the site.
- **What stays:** the email and Discord code is unchanged and tested. Switching either back on takes its secrets and a one-line change (`monitor.watch.ACTIVE`).

## Built

- **Groundwork from earlier** (`monitor/`):
  - holdings per lot, derived from trades and corrections
  - alert rules: tiers, no repeats unless worse, one grouped message per channel, quiet hours 9 pm to 7 am Central, per-holding snooze, the monthly noise report
  - email (SMTP) and Discord (webhook) delivery, each retried 3 times and never logging the password or webhook
- **The holdings watch** (`monitor/watch.py`, `.github/workflows/watch.yml`), new 2026-10-28:
  - **When:** every hour on weekdays, 7 am to 6 pm Central. GitHub's cron is UTC and ignores daylight saving, so it fires 12:17 to 00:17 UTC and the job skips any hour outside the watch.
  - **What it checks, for each holding:**
    - new 8-Ks from SEC submissions (red-flag items are urgent, any other 8-K is informational)
    - the live price against yesterday's close (a drop of 10% or more is urgent)
  - **Delivery:** alerts go through the rules above to the app channel. Every decision (sent, held or suppressed) is appended to the `alerts` table, which is what the Today screen will read.
  - **The 7 am run** releases what quiet hours held. That settles open question 3 from M3, decided below.
  - **Failures:** a failing source (an 8-K fetch or a quote) is printed loudly and fails the run, after the alerts that did work are recorded.
  - **One writer:** it shares the nightly run's `r2-writer` concurrency group, so the two never write the database at once.
  - **Test alert:** a manual run can send one.

## Decisions I made (yours to veto)

1. **Red-flag 8-K items (urgent):**
   - 1.03 bankruptcy or receivership
   - 1.05 material cybersecurity incident
   - 2.06 material impairment
   - 3.01 delisting notice or listing rule failure
   - 4.01 change of auditor
   - 4.02 past financial statements can no longer be relied on

   Every other 8-K on a holding is informational. Item 5.02 (officer changes) isn't urgent, because the item alone can't tell a CEO leaving from a routine board appointment. Reading the text needs the agent, which can come later.
2. **A run at 7 am,** so held alerts go out at 7 as the plan says, rather than at 8.
3. **"10%+ drop" includes exactly 10%,** measured against yesterday's close.
4. **Quiet hours still apply to the app.** An alert made at night is recorded as held and shows from 7 am. That keeps the rules the same if push channels come back. If you'd rather the site show night alerts right away, it's a one-line change.

## Limits to know

- **The watch and the nightly share one concurrency group** (one database writer at a time). GitHub keeps at most one waiting run per group, and a newly queued run cancels the one already waiting. A nightly that's waiting when a watch run queues would be cancelled. Their schedules don't overlap (watch 12:17 to 00:17 UTC, nightly 01:17), so it takes a long GitHub delay or a manual run to hit. A cancelled nightly shows in the run list, and a manual rerun covers it.

- **GitHub can start scheduled runs late,** sometimes by hours (the first nightly started 5.5 hours late).
- **Actions minutes:** about 13 runs per weekday at 1 to 2 minutes each is roughly 400 to 500 minutes a month, on top of the nightly run's roughly 550. That's under the 2,000 free minutes, but worth watching (the plan's "Actions minutes measured" check).
